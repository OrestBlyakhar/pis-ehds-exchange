# ADR 0001. FHIR R4, аудит у тій самій транзакції, окрема схема vault

Задача PIS-30.

## Статус

Прийнято для прототипу. Відкриті розбіжності вичитки цим записом не закриваю.

## Контекст

Обмін має два контури. Лікар закладу-отримувача забирає ідентифікований набір для лікування. Дослідник забирає один псевдонімізований знімок за дозволом. Згода, перевірка доступу і журнал входять у саму видачу.

D4 уже фіксує канонічний формат FHIR R4 JSON, а CSV лише як похідний файл знімка. D7 фіксує HMAC-SHA256 і окрему схему `vault`. `nfr.md` фіксує одну транзакцію на рішення і рядок аудиту, і зупинку обміну, якщо PostgreSQL недоступна. Цей ADR збирає ці три рішення в одне місце, щоб PIS-31, PIS-34 і PIS-36 не вибирали їх наново.

## Рішення

1. Канонічний обмін — HL7 FHIR R4, JSON. Лікування віддає Bundle. Дослідження віддає FHIR JSON того самого знімка і похідний CSV. CSV не є другим джерелом правди.
2. Рішення про видачу і рядок журналу аудиту пишуться однією транзакцією PostgreSQL 16. Немає режиму «віддати дані, журнал дописати пізніше». Якщо запис аудиту не пройшов, транзакція відкочується і клінічні поля у відповідь не потрапляють. Якщо PostgreSQL недоступна, обмін зупиняється і журнал не обходиться.
3. Псевдоніми, зв’язок псевдонім–пацієнт і секрет HMAC лежать у схемі `vault`, окремо від клінічних таблиць і від файлу знімка. Секрет не потрапляє у frontend. Роль застосунку, якою відкривається знімок дослідника, `vault` не читає.

Стек виконання цих рішень уже заданий: FastAPI, PostgreSQL 16, React (Vite), один локальний екземпляр. ADR процес не замінює і код не додає.

## Наслідки

- Схема PostgreSQL (PIS-31) має щонайменше `clinical` і `vault`. Журнал у `clinical` без `UPDATE` і `DELETE` для ролі застосунку.
- API лікування (PIS-34) віддає FHIR Bundle лише після тієї самої транзакції, що пише аудит.
- Дослідницький знімок будується поверх `vault`, але дослідник бачить лише псевдонімізований файл.

## Що не вирішую

- A-07 віддає в аварійному доступі також Observation. UC-04 AC2 лабораторний архів у цей шлях не пускає. Формат FHIR це не знімає.
- Словник FHIR кладе код `managingOrganization` у дослідницький знімок. Розділ 2.2 формалізації прибирає ідентифікатор закладу. ADR не обирає, чи є цей код у файлі.
- PIS-17 ставить 500 мс на лікування і 2 с на знімок. Чернетка розділу 8.4 ставить стелю 3 с на запит лікування до 50 ресурсів. Жодне з чисел не скасовую.
- Activity UC-06 каже «зсув дат». Розділ 8.5 тримає стале зміщення ±7 діб у `vault`. Словник FHIR для клінічних дат знімка пише місяць і рік. Окрему схему `vault` я фіксую. Спосіб узагальнення дати — ні.
- A-17 не дає жодній ролі читати секрет HMAC. Клас K5 у розділі 8.5 віддає DG таблицю відповідності, секрет і зміщення дат, і кожне таке читання пише журнал. Секрет лишається у `vault`. Чи має DG окреме читання, не обираю.

# НФВ, узгоджені зі стеком

Задача PIS-17. Три теми з опису: час відповіді, fail-closed аудит, локальний запуск.

Числових порогів і назви мови в описі PIS-17 немає. Файла `stage-1-and-requirements.md`, на який спирається PIS-10, у віддаленому репозиторії теж немає. Пороги часу нижче — домовленість цієї задачі для локального прототипу, не лікарняний SLA. PostgreSQL, FHIR R4, окрема схема vault і аудит у тій самій транзакції вже названі в PIS-27, PIS-30, PIS-31 і PIS-36. Мову API тікети не фіксують; її зафіксовано тут.

## Стек

| Частина | Рішення | Навіщо для цих НФВ |
| --- | --- | --- |
| База | PostgreSQL 16, одна база, схеми `clinical` і `vault` | Одна транзакція на клінічний запис і аудит. Ключ HMAC лежить у `vault`, окремо від EHR. |
| API | Python 3.12, FastAPI, Uvicorn на `127.0.0.1:8000` | Локальний HTTP для FHIR JSON однією командою. Мову можна змінити окремим ADR, якщо команда обере іншу. |
| Контракт даних | FHIR R4, обмін лікування — Bundle | Уже зафіксовано в PIS-30 і PIS-34. Цей файл API не реалізує. |
| UI | Окремий локальний клієнт, лише через API | Екрани лишаються за PIS-38–PIS-42. Фреймворк UI тут не обирається. |

Схему таблиць робить PIS-31. Маршрути обміну робить PIS-34. Тут немає коду сервера і немає `docker-compose`.

## Час відповіді

Міряти на машині розробника, сервер і PostgreSQL на `localhost`, без мережі між закладами. Обмін між закладами в прототипі імітується локально.

| Операція | Поріг |
| --- | --- |
| Лікування: перевірка згоди, читання EHR одного пацієнта, запис аудиту, відповідь Bundle | не довше 500 мс |
| Дослідницький знімок до кількох десятків пацієнтів, включно з відмовою якщо пацієнтів менше ніж 5 | не довше 2 с |
| Відмова доступу (немає згоди, чужа роль, прострочений дозвіл) | не довше 500 мс, без клінічного тіла |

Час аудиту входить у поріг, бо запис аудиту не відкладається на потім. Якщо поріг зірвано, це дефект прототипу, а не привід віддати дані без журналу.

## Fail-closed аудит

Клінічні дані і рядок аудиту пишуться однією транзакцією PostgreSQL. Це те саме правило, що в PIS-30 («аудит у тій самій транзакції») і в PIS-36 (журнал лише на додавання).

- Якщо `INSERT` аудиту не пройшов, транзакція відкочується. API не повертає FHIR Bundle і не повертає клінічні поля в тілі помилки.
- Немає режиму «віддати дані, журнал дописати пізніше».
- Відмова через згоду, роль або поріг групи теж лишає слід у журналі. Якщо не вдалося записати навіть цю відмову, відповідь — помилка без клінічних даних.
- Аварійний доступ (правило A-07 з PIS-15) відкриває клінічні класи лише після запису причини в журнал, до віддачі даних. Той самий fail-closed.
- Роль застосунку не має `UPDATE` і `DELETE` на таблиці журналу. Це закриває PIS-36; тут лише умова, яку схема має виконати.

Сховище псевдонімів не рятує від цього правила: дослідницький CSV теж не віддається, якщо рядок аудиту не записано.

## Локальний запуск

Прототип має підніматися на машині розробника без хмари.

1. PostgreSQL 16 слухає `127.0.0.1:5432`. У одній базі дві схеми: `clinical` (EHR, згода, аудит) і `vault` (ключ HMAC, псевдоніми). Контейнер чи локальна установка — байдуже, аби порт і схеми були ті самі.
2. API слухає `http://127.0.0.1:8000`. Очікувана команда, коли з’явиться код PIS-34:

```text
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

3. UI відкривається локально і звертається лише до цього API.
4. Ознака, що процес живий і не чіпає клінічні таблиці: `GET /health` відповідає `200` і порожнім службовим тілом. Маршруту ще немає.

Поки немає схеми і коду API, цей репозиторій свідомо не запускається. Команди вище — контракт для PIS-31 і PIS-34, а не інструкція, яка має спрацювати на поточному коміті.
